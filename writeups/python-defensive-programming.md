# Secure Flask Application with Defensive Programming

## Overview

This project focused on improving the security, reliability, and maintainability of an existing Python Flask application by implementing defensive programming techniques. After reviewing the application source code, network security logs, and static analysis reports, I identified several areas where invalid user input, missing validation, and insufficient error handling could negatively impact the application.

The primary goal of this project was to strengthen the application's ability to safely handle unexpected input while preserving its original functionality. This was accomplished by implementing assertions, input validation, structured logging, and exception handling throughout the application. After completing the code changes, automated testing and manual verification were performed to confirm the security improvements functioned as expected without introducing regressions.

---

# Project Objectives

The objectives of this project were to:

- Review an existing Flask application for security and reliability weaknesses.
- Implement defensive programming techniques to improve application stability.
- Validate user input before processing requests.
- Improve application visibility through structured logging.
- Prevent common runtime failures by handling expected exceptions.
- Verify the security improvements through automated and manual testing.
- Document the code changes and explain the security benefits of each improvement.

---

# Initial Assessment

Before making any modifications, I reviewed the Flask application, the provided network security log, and the static analysis reports generated by Flake8 and Bandit.

The review identified several opportunities to improve both security and reliability.

- User input was accepted with minimal validation.
- Critical values were processed without verification.
- Invalid equipment selections could generate runtime exceptions.
- Rental duration values could produce invalid calculations.
- Application activity relied primarily on console output instead of structured logging.
- Failed login attempts and suspicious activity were not consistently recorded.

These findings established the roadmap for the defensive programming improvements implemented throughout the project.

## Assertion Added for Username Validation

### Purpose

The username validation function was updated to verify that the submitted username is a non-empty string before checking whether it belongs to an approved user.

### Before

```python
def validate_username(username):
    allowed_users = {"admin", "alice", "bob", "charlie"}
    return username in allowed_users
```

### After

```python
def validate_username(username):
    """
    Validates that the username is allowed.
    """
    try:
        assert isinstance(username, str) and username.strip() != "", \
            "Username must be a non-empty string"
        logging.info("Username assertion passed.")
    except AssertionError as error:
        logging.warning(f"Username validation failed: {error}")
        return False

    allowed_users = {"admin", "alice", "bob", "charlie"}
    return username in allowed_users
```

### Security Improvement

The assertion verifies that the username is a valid string before checking whether it exists in the approved user list. If the assertion fails, the application records a warning and safely rejects the request instead of continuing with invalid data.

### Failure Prevented

Before this change, the application only checked whether the username existed in the approved user list. An empty username such as "" or an unexpected value such as None could still be passed into the validation function without identifying the reason for failure. The updated assertion rejects invalid input before authentication begins and records the event in the troubleshooting log.

## Assertion Added for IP Address Validation

### Purpose

The login process was updated to verify that the client IP address exists and is stored as a valid string before determining whether it should be treated as suspicious.

### Before

```python
ip_address = request.remote_addr

if not ip_address.startswith(("192.168.", "10.", "127.")):
    print(f"Suspicious external IP detected: {ip_address}")
```

### After

```python
ip_address = request.remote_addr

assert ip_address is not None and isinstance(ip_address, str), \
    "Invalid IP address"
logging.info("IP address assertion passed.")

if not ip_address.startswith(("192.168.", "10.", "127.")):
    logging.warning(f"Suspicious external IP detected: {ip_address}")
```

### Security Improvement

The added assertion confirms that the application received a usable IP address before calling the `startswith()` method. Suspicious external IP addresses are also recorded as warning-level events instead of only being displayed in the console.

### Failure Prevented

If `request.remote_addr` returned `None`, calling `startswith()` would generate an `AttributeError` and interrupt the login request. The assertion prevents the application from attempting to process an invalid IP address and records the event for future review.

## Input Validation for Rental Duration

### Purpose

The rental workflow was updated to reject rental durations that are zero or negative before calculating the total rental cost.

### Before

```python
days = int(days_str)
total_cost = daily_rate * days
```

### After

```python
days = int(days_str)

if days <= 0:
    flash("Rental days must be greater than zero.", "danger")
    return render_template(
        "rent.html",
        rental_result=rental_result
    )

total_cost = daily_rate * days
```

### Security Improvement

The application now validates the rental duration before calculating the total cost. Only values greater than zero are accepted for processing.

### Failure Prevented

Before this validation was added, users could submit values such as `0` or `-5`, allowing the application to calculate invalid rental totals. The updated validation rejects these values before any calculations occur and informs the user that a valid rental duration is required.

## Exception Handling for Invalid Equipment Selection

### Purpose

The equipment lookup was placed inside a `try/except` block so the application could safely handle equipment names that do not exist in the pricing dictionary.

### Before

```python
daily_rate = EQUIPMENT_PRICES[equipment_type]
```

### After

```python
try:
    daily_rate = EQUIPMENT_PRICES[equipment_type]

except KeyError:
    logging.error(
        f"Invalid equipment type selected: {equipment_type}"
    )
    flash("Invalid equipment type selected.", "danger")
```

### Security Improvement

The application now catches the expected `KeyError` instead of allowing the exception to terminate the request. The invalid equipment selection is recorded in the troubleshooting log while the user receives a clear error message.

### Failure Prevented

Before this change, entering an equipment type that did not exist in the pricing dictionary, such as `"Forklift"`, caused a `KeyError` and interrupted the rental process. The updated code handles the exception gracefully, records the error, and allows the application to continue running.

## Exception Handling for Invalid Rental Duration

### Purpose

The application was updated to safely handle rental duration values that cannot be converted into integers.

### Before

```python
days = int(days_str)
```

### After

```python
try:
    days = int(days_str)

except ValueError:
    logging.error(
        f"Invalid number of days entered: {days_str}"
    )
    flash("Rental days must be a valid number.", "danger")
```

### Security Improvement

The application now catches invalid numeric input before it causes an unhandled exception. Invalid values are recorded in the troubleshooting log while the user receives a helpful message explaining the error.

### Failure Prevented

Before this change, entering values such as `"five"` or `"abc"` caused a `ValueError` and interrupted the request. The updated exception handling safely catches the error, records the invalid value, and allows the application to continue running.

## Structured Application Logging

### Purpose

Python's built-in `logging` module replaced console output with structured application logging to improve troubleshooting and provide a record of important application events.

### Before

```python
print("Starting application...")
print(f"Login attempt - Username: {username}, IP: {ip_address}")
print(f"Calculated cost: {total_cost}")
```

### After

```python
logging.basicConfig(
    filename="Troubleshooting_012802954.log",
    level=logging.INFO,
    format="%(asctime)s - %(levelname)s - %(message)s"
)

logging.info("Starting application...")
logging.info(f"Login attempt - Username: {username}, IP: {ip_address}")
logging.info(f"Calculated cost: {total_cost}")
logging.warning(f"Login failed for {username}.")
logging.error(f"Invalid equipment type selected: {equipment_type}")
```

### Security Improvement

Structured logging records informational events, warnings, and errors in a persistent log file instead of displaying them only in the terminal. This provides an audit trail that supports troubleshooting and security monitoring.

### Failure Prevented

Before logging was implemented, important application events could be lost when the terminal closed. Failed login attempts, invalid requests, and application errors were difficult to investigate after execution. The troubleshooting log now preserves those events for later review.

# Security Impact

Implementing defensive programming significantly improved the application's overall security and reliability. Assertions validate important assumptions before processing continues, reducing the likelihood of invalid data reaching the application logic. Input validation prevents invalid rental durations from producing incorrect calculations, while specific exception handling allows expected runtime errors to be handled safely instead of interrupting execution. Structured logging also provides administrators with a detailed record of application activity, making troubleshooting and security investigations much easier.

Together, these improvements make the application more resilient against invalid input while preserving the expected functionality for legitimate users.

# Out of Scope and Future Improvements

This project focused on implementing the defensive programming techniques required by the assignment. Several additional security improvements would be recommended before deploying the application in a production environment.

Future improvements include:

- Store user passwords using secure password hashing instead of comparing plaintext values.
- Implement role-based access control to separate user and administrator permissions.
- Move the Flask secret key into an environment variable or centralized secrets manager.
- Add rate limiting to protect the login page against brute-force attacks.
- Store application data in a database instead of hardcoded values.
- Enable HTTPS to encrypt data transmitted between clients and the server.
- Integrate continuous static analysis and automated testing into a CI/CD pipeline.
- Centralize application logs using a log management platform for improved monitoring and alerting.

Although these improvements were outside the scope of this project, they would further strengthen the application's overall security posture.

# Lessons Learned

This project reinforced the importance of defensive programming when developing secure software. Implementing assertions, input validation, exception handling, and structured logging demonstrated how relatively small code changes can significantly improve application reliability and make security issues easier to identify.

The project also reinforced the importance of automated testing. Running the pytest test suite after each modification verified that the defensive programming improvements did not introduce regressions while confirming that the application continued to function correctly.

One of the biggest lessons learned was that secure software development is not only about preventing attacks. It also involves validating input, handling expected failures safely, recording meaningful events, and making applications easier to troubleshoot and maintain.
